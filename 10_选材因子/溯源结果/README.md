### 检索通道的现状（下一轮开工前先看这段）

> ⚠️ **这一节在 2026-09-27 晚被实测推翻过一次，改写过。**
> 收尾时写的是「可用通道基本全灭」。十路并行开工后，多个会话**各自独立**测出
> **有两条通道是通的，而且不吃 WebSearch 配额**。原结论已作废，以本节的实测结果为准。
> 教训：**「WebSearch 配额打满」≠「搜不动了」**——写「全灭」之前要先试过 WebFetch 这条路。

#### 先说一个最容易搞错的区分

**WebSearch 的 200 次额度是「会话级共享」的**，不是每个子会话各发一份。
子 agent 报的错误原文是 `this session has used its web search budget (200 of 200)`，
而且**在它开工前就已被同会话的其他 agent 消耗掉了**——实测某会话只发出约 18 次检索就被截断。

所以：**在一个会话里放 N 个子 agent，拿到的仍然是一份 200 次配额，不是 N 份。**
要拿到多份配额，必须**开独立的 Claude Code 会话**（那是独立的 session）。

**但是**——下面这几条通道走的是 `WebFetch` / `fetch.py`，**不消耗那 200 次**。
配额打满之后，它们照样能用。这才是上一轮真正漏掉的一层。

#### 实测可用（不吃 WebSearch 配额）

| 通道 | 用法 | 关键坑位 |

#### ★ 出口竞争：通道的额度是**按出口 IP 先到先得**的

这一条解释了一堆看起来互相矛盾的报告，**是本节最该记住的东西**。

十路并行开工后，**同一条通道在不同会话嘴里完全相反**：
会话 5 说 `r.jina.ai` 全程可用（约 40 余次，零 429），会话 4 说它**后半段开始 403**；
360 站内检索也是这样——会话 4 说「开局很好用，**用几次后开始 302 到 `qcaptcha.so.com` 验证码墙**」。

把这些并排看，结论**不是**「谁报错了」，也**不是**「WebFetch 通、本地一定不通」，
而是更深的一层：

| 取数方式 | 从哪出去 | 会不会被其他会话抢 |
|---|---|---|
| **`WebFetch`** | Anthropic 侧 | **不抢**，各出各的 |
| **本地 `curl` / `fetch.py`** | **本机那一个出口 IP** | **会抢**——十个会话共用一个 IP |

所以**「同一条通道，有人通、有人 403」不是矛盾，是抢**：
谁先跑到谁拿到额度，后到的撞墙。会话 5 跑得早、吃到 40 余次；
会话 4 跑得晚、撞上验证码墙——**两个报告都是真的，都不必撤回。**

**推论一（最要紧）**：**旁路通道不是无限量的，它有额度，而且按出口 IP 算。**
所以新会话开工要**把最难的词排在最前面搜**，别拿旁路去扫长尾词。
（这条是会话 4 主动提的，很有价值。）

**推论二**：遇到 403 / 429 / 验证码，**先换取数方式，再换通道**——
本地不通试 `WebFetch`，`WebFetch` 不通试本地。两者出口不同，
**一个被抢了，另一个可能正好空着**，成本极低。

**推论三**：并行开工时**能走 `WebFetch` 就走 `WebFetch`**，
别十个会话一起拿本地 `curl` 去挤同一个 IP。

**推论四**：选通道要优先选**按会话/按请求计**的，而不是**按 IP 计**的。

#### `r.jina.ai` 的边界（实测）

- **能取**：`baijiahao.baidu.com`（百家号正文，会话 5 的关键突破）、
  `html.duckduckgo.com`、`news.southcn.com`、`sohu.com`、`163.com`、`toutiao.com`、
  各类政务网（`gaozhou.gov.cn` / `yunfu.gov.cn`）、`mm111.net`
- **取不到**：`epaper.nfnews.com`（南方日报电子报，302 跳首页）、
  `www.nfnews.com` 的南方+前端壳页（只返回导航壳，无正文）、
  `web.archive.org`（返回空/超时）
- **Bing 经 jina**：返回地图类无关兜底结果，**无效**（与必应直接抓同一个毛病）
- **Sogou 经 jina**：能用但噪声极大，只在 DDG 空手时补一枪

#### 取原文最可靠的做法：`curl` + 去标签，不是 WebFetch

**`WebFetch` 会以版权为由拒斥长段逐字复现**（上面那条中央媒体拒载是同一个原因）。
实测最稳的是 **`curl` 拿原始 HTML + Python 去标签**——这也正是全项目
「原文一律由脚本从页面快照拷贝」那条约定的由来。

#### 一条能救命的旁路：中央媒体的转载页

**`WebFetch` 对人民网等中央媒体页会以版权为由直接拒载**（实测 `cpc.people.com.cn` 被拒）。
但**改走财政部 / 发改委 / 地方政府网站的转载页，用 `_tools/fetch.py` 就能拿到逐字全文**。
实测靠这条拿到了《人民日报》2021-12-30 那篇江陵报道的全文。

**所以中央媒体稿不要直接抓原站**——先搜标题，找转载页，再 fetch。

#### 还有一条与取材源有关的硬约束

**注意时间窗**。上一轮曾把《大众日报》2024-08-06 一篇齐河报道当作某段的候选源，
但该卷笔试日是 **2023-02-25**——**刊发日晚于笔试日一年半，结构上不可能是取材源**。
判「疑似原型」之前，先对一遍刊发日与笔试日。`_核对/结构缺口.md` 里记着各卷的笔试日期。

`finalize.py` 会先重建 `_parts` 再填判断项，`bucha.py` 会先切掉上一次追加的补查节再重写，
所以整条链可以反复跑，不会越堆越多。判断项（对应程度、匿名对象识别、补充来源）写在
`finalize.py` 顶部的 `JUDGE` 和 `MANUAL` 两张表里，补查内容写在 `bucha.py` 里。

### 三条工具上的约定

**原文一律由脚本从页面快照拷贝，不经过人手转写**——这是唯一能保证「逐字」的办法。
不用 WebFetch 的原因也在这里：它会以版权为由拒绝逐字转载正文，只给摘要；而摘要不能当原文贴。

**`fetch.py` 的 UA 会轮换**。有的站（搜狐就是）会按频率随机 403，同一个 UA 连撞三次白费；
换一个 UA 往往就过了。所以 `attempts` 里每次换一个 UA，而不是重试同一个。

**`_cache/` 是共用的**，因此 `_tools/cache_manifest.json` 列明「哪些页面算 2025 省市卷的来源」。
不设这个清单，做别的年份时抓进来的页面会被误当成这一卷的来源。

## 核验是怎么做的

分两层，**两层不能互相替代**：

- **字**：各卷核验环节从交付件里挑出贴了原文的链接，用 `fetch.py --check "<那句原话>"`
  对着活页面逐字计数，命中 0 次即判不通过。有几卷还做了**阴性对照**——故意贴一句编造的假原文，
  确认工具确实返回 NOT_FOUND，排除「工具恒真」。
- **链**：`linkcheck_all.py` 把 12 份交付件里的来源链接**全部**重开一遍（243 条），
  只筛「页面能不能打开、有没有正文」。这一层能发现抽样发现不了的死链。

抽样能证明「贴出来的原文是真的」，不能证明「剩下的链接还活着」——所以补了第二层。

**两层都查不出「有的段根本没做」**。2025县镇、2026县镇就是这么漏过去的：核验环节抽了
17 条、19 条贴出来的原文，条条对得上，于是判「可信」；可这两卷里还有一批段标着
「本轮未完成」——原文压根没贴，抽样自然抽不到。查这类缺口只能靠**通读交付件找「本轮未完成」
这类自曝标记**，或者数「段标题」与「对应程度行」对不对得上。这一次是数出来的：
2025县镇 22 个段标题对 26 行对应程度，多出来的 4 行正是四则没做完的材料。
